# Kịch bản Thuyết minh — Phần 2: API Testing

## Slide 4 — Chuyển phần 2: API Testing (Section Divider)
- **Mục tiêu**: Báo hiệu bước vào chương API Testing.
- **Lời thoại gợi ý**: "Bây giờ chúng ta đi vào Phần 2: Kiểm thử API từ khái niệm cơ bản, status code, authentication cho đến thiết kế test case và công cụ thực hành."

## Slide 5 — API là gì?
- **Mục tiêu**: Làm rõ định nghĩa API và cấu trúc HTTP Request/Response.
- **Lời thoại gợi ý**: "API là cầu nối giữa Client và Server. Một request gồm Method, URL, Headers và Body; trong khi Response trả về Status Code, Headers và Body dữ liệu."

## Slide 6 — Đọc kết quả API bằng Status Code
- **Mục tiêu**: Hướng dẫn phân loại status code (2xx, 4xx, 5xx).
- **Lời thoại gợi ý**: "Status code là tín hiệu đầu tiên phản ánh kết quả gọi API. Chúng ta tập trung vào 200/201 cho thành công, 400/401/404 cho lỗi client, và 500/503 cho lỗi phía server."

## Slide 7 — API có Authentication vs Authorization
- **Mục tiêu**: Phân biệt giữa xác thực danh tính (AuthN) và phân quyền truy cập (AuthZ).
- **Lời thoại gợi ý**: "Authentication trả lời câu hỏi 'Bạn là ai?', còn Authorization xác định 'Bạn được làm gì?'. Mọi test suite API bắt buộc phải kiểm tra cả hai khía cạnh này."

## Slide 8 — Các cơ chế xác thực phổ biến
- **Mục tiêu**: Giới thiệu các chuẩn auth thực tế (Basic, API Key, Bearer Token, OAuth2).
- **Lời thoại gợi ý**: "Tùy thuộc vào kiến trúc, hệ thống có thể dùng Basic Auth, API Key hay Bearer Token với JWT/ISO-timestamp như bài lab mẫu của nhóm."

## Slide 9 — Các loại Test Case cho API
- **Mục tiêu**: Liệt kê 6 loại test case cơ bản (Happy Path, Negative, Auth, Validation, Schema, Boundary).
- **Lời thoại gợi ý**: "Một bộ API test chuyên nghiệp không chỉ test trường hợp chạy đúng (Happy path), mà phải bao phủ lỗi validation, sai auth, vi phạm schema và giá trị biên."

## Slide 10 — Kỹ thuật nâng cao để mở rộng coverage
- **Mục tiêu**: Giới thiệu các kỹ thuật phân tích thiết kế test (EP, BVA, Pairwise, DDT).
- **Lời thoại gợi ý**: "Để đạt coverage cao mà không bùng nổ số lượng test case, chúng ta áp dụng Equivalence Partitioning, Boundary Value Analysis và Data-driven Testing."

## Slide 11 — Postman — Tổng quan (Part 1)
- **Mục tiêu**: Giới thiệu công cụ Postman và các thành phần cốt lõi.
- **Lời thoại gợi ý**: "Postman là môi trường thử nghiệm API phổ biến để gửi request, quản lý collection và chuẩn hóa test. Điểm cốt lõi là Collection, Environment, Variable và Script."
- **Chú thích**: Giải thích ngắn sự khác nhau giữa Environment và Variable nếu người nghe hỏi.

## Slide 12 — Postman — Tính năng nâng cao (Part 2)
- **Mục tiêu**: Giới thiệu Collection Runner, Data-driven CSV/JSON, Monitor và Mock Server.
- **Lời thoại gợi ý**: "Khi mở rộng, Postman cho phép chạy theo data file, tạo Mock Server giả lập backend và theo dõi API bằng Monitor mà không cần rời khỏi cùng một workspace."

## Slide 13 — Postman — Tổ chức Collection
- **Mục tiêu**: Hướng dẫn cấu trúc thư mục Collection tiêu chuẩn và cách đặt biến dùng chung.
- **Lời thoại gợi ý**: "Nhóm tổ chức Collection theo từng nhóm endpoint, dùng biến collection-level cho baseUrl và auth chung, còn từng request chỉ giữ phần khác biệt của test case."

## Slide 14 — Postman — Script & Assertion
- **Mục tiêu**: Giải thích Pre-request script và Test script với Chai Assertion.
- **Lời thoại gợi ý**: "Pre-request script dùng để chuẩn bị token, timestamp hoặc dữ liệu động trước khi gửi. Test script kiểm tra status code, response body, thời gian phản hồi và các biến cần truyền sang request tiếp theo."
- **Chú thích**: Nhấn mạnh script trong Postman là JavaScript chạy trong ngữ cảnh từng request.

## Slide 15 — Data-driven Testing
- **Mục tiêu**: Minh họa sức mạnh của việc tách biệt Test Script và Test Data.
- **Lời thoại gợi ý**: "Nhờ Data-driven Testing, chúng ta chỉ viết script một lần nhưng có thể kiểm thử hàng chục kịch bản khác nhau thông qua file dữ liệu JSON hoặc CSV."

## Slide 16 — Postman — Quy trình sử dụng thực hành
- **Mục tiêu**: Chốt lại luồng sử dụng Postman từ request thủ công sang test suite có cấu trúc.
- **Lời thoại gợi ý**: "Một quy trình Postman thực tế sẽ đi từ tạo request, gắn biến môi trường, thêm pre-request script, viết assertion rồi chạy lại collection để kiểm tra cả luồng nghiệp vụ."
- **Chú thích**: Nói đây là luồng khuyến nghị để người xem hiểu cách dùng thực tế, không phải quy tắc cứng.

## Slide 17 — VS Code REST Client
- **Mục tiêu**: Đưa ra giải pháp thay thế nhẹ nhàng ngay trong editor.
- **Lời thoại gợi ý**: "Với các lập trình viên thích thao tác nhanh trong code, VS Code REST Client cho phép gửi request trực tiếp từ file `.http` mà không cần bật ứng dụng nặng."

## Slide 18 — API mẫu: Product Service (Part 1 - Overview & Schema)
- **Mục tiêu**: Giới thiệu kiến trúc Node.js/Express in-memory của Product Service.
- **Lời thoại gợi ý**: "API thử nghiệm của nhóm là Product Service viết bằng Node.js/Express, lưu trữ in-memory để đảm bảo các kịch bản kiểm thử lặp lại ổn định."

## Slide 19 — Endpoint của Product Service (Part 2 - Endpoints & Auth)
- **Mục tiêu**: Bảng chi tiết 5 endpoints CRUD và cơ chế Authorization header.
- **Lời thoại gợi ý**: "Service cung cấp 5 endpoint CRUD đầy đủ (GET, POST, PUT, DELETE). Mọi endpoint đều yêu cầu Authorization header dạng Bearer timestamp hợp lệ."
